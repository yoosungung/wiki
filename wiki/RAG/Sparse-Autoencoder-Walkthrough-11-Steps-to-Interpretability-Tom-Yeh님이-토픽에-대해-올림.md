# Sparse Autoencoder Walkthrough 11 Steps to Interpretability | Tom Yeh님이 토픽에 대해 올림

Sparse Autoencoder by hand ✍️ ~ 11 steps walkthrough below How do you find out what a model is actually representing inside? A Sparse Autoencoder (SAE) takes the dense activations a model produces and maps them into a much wider, mostly zero space. Then the remaining non-zeros are individual features that start to mean something you can name. Anthropic's "Scaling Monosemanticity" did this to Claude 3 Sonnet and pulled out features for concepts like the Golden Gate Bridge. Goal: map each 3D activation into a 6D space where only a couple of features are positive and the rest are zero. = 1. Given = The transformer's output: activations for five tokens, three numbers each. They work, and not one of them is interpretable. = 2. Encoder linear layer = Multiply x by the encoder weights and add the biases. Three dimensions become six: wider, not narrower. = 3. ReLU = Set every negative to zero. What survives is f, the sparse features: 21 of these 30 numbers are now zeros. I picked the weights and biases so ReLU would flatten most of the grid, because sparsity is the whole point. Interpretability arrives when only one or two features are positive. x4 and x5 are each positive at exactly one feature, f5, the row labelled Park. Whatever f5 means is what those two tokens have in common, and both of them show a park. = 4. Reconstruction = Multiply f by the decoder weights and add the biases to get x', the reconstruction of x from interpretable features. It is still some distance from x. Closing that distance is what training does. = 5. Decoder weight norms = Compute the L2 norm of each decoder weight column: 1, 1, √2, 1, √2, 1. Step 9 needs them. = 6. L1 sparsity loss = Sparsity means we want as many values in f to be zero as possible. L1 is the sum of the absolute values, and we want that sum to be small. = 7. L1 gradient = The gradient of L1 is -1 wherever f is positive, which makes intuitive sense: we want those values to come down to zero. = 8. Zero stays zero = Where f is already zero, the gradient is zero. There is nothing there to change. = 9. Weight the gradient = Multiply each gradient row by that feature's decoder weight norm. Without it the model can cheat: shrink f, inflate the decoder weights to compensate, and reconstruct x just as well while the sparsity loss reports a job well done. = 10. L2 reconstruction loss = Reconstruction means we want the difference between x and x' to be as small as possible. = 11. L2 gradient = The gradient is simply x - x' times 2. With both sets of gradients in hand, run backpropagation and update both encoder and decoder, until sparsity and reconstruction balance. 💾 Save this post!

Google DeepMind's new ECCV 2026 paper argues that era is ending: the replacement is hiding inside video generators. GenCeption takes a pre-trained text-to-video diffusion model and converts it into a single, feed-forward vision model. One backbone, one head, steered by text instructions: ask for "depth", "segmentation" or "keypoints" and the same network answers in a single forward pass. 𝗪𝗵𝘆 𝗶𝘁 𝗺𝗮𝘁𝘁𝗲𝗿𝘀: video generative pretraining forces a model to learn geometry, motion and physics to predict pixels. 𝗞𝗲𝘆 𝘁𝗲𝗰𝗵𝗻𝗶𝗰𝗮𝗹 𝗵𝗶𝗴𝗵𝗹𝗶𝗴𝗵𝘁𝘀: 1. Unified architecture: dense tasks (depth, normals, segmentation) are predicted in RGB ambient space; sparse tasks (camera pose, keypoints) use learnable tokens added to the diffusion transformer. 2. Single-step inference: the multi-step generative backbone collapses into one feed-forward pass, no iterative denoising. 3. Extreme data efficiency: comparable performance to D4RT and VGGT-Ω with 7x to 500x fewer training frames, and it beats V-JEPA and VideoMAE V2 under matched fine-tuning data. 4. Language-grounded segmentation: it segments objects from referring expressions (color, spatial relations, motion), even objects never seen in fine-tuning. 5. 4D understanding: per-pixel geometry plus camera pose lift a single video into a grounded 4D point cloud. - A keyboard can cost $500 and still be useless if the software behind it takes three menus to do what one keypress could. That's the whole thesis behind ShiftKey, and it's why I spend as much time prototyping interaction models and focusing on the user experience as I do designing PCBs. This week I've been prototyping something new: a dedicated agent launcher. Hold down one key. A radial menu opens around your cursor. Each slice is a different AI agent, tool, or app. Nudge the mouse toward the one you want, release, and a clean instance opens instantly. No alt-tab, no bookmarks bar, and no single key that is perpetually mapped to one specific agent you don't even use. The interesting part isn't the AI. It's the interaction. Right now, opening any AI agent still means treating it like a website: click, wait, load, type. That's old interaction design applied to a new category of tool. As the number of agents you actually use in a day goes from one to five to fifteen, the cost of switching between them stops being trivial. Radial menus solve this because they trade memory for motion: instead of remembering a name or hunting a taskbar, your hand just learns a direction. It's the same reason pie menus outperform dropdowns in high-frequency tasks: spatial memory is faster than linguistic memory. That's a hardware problem as much as a software one. A dedicated physical key means the gesture never has to compete with whatever's already open on your screen. I'm deciding right now whether this becomes a native ShiftKey feature that you can assign to any key or button.
