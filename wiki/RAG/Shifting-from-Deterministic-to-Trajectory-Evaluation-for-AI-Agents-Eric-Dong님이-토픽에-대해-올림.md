## Shifting from Deterministic to Trajectory Evaluation for AI Agents

이 제목은 아래 게시물에서 AI가 요약한 것입니다.

If your AI agent evaluation strategy is just checking the final text response, you’re debugging completely blind. 🙈 In traditional software, testing is deterministic. In early GenAI, input-output prompt testing was enough. Autonomous AI Agents break this model entirely. A single prompt triggers dozens of internal reasoning steps, API calls, dynamic retrievals, and state mutations across multi-turn conversations. The biggest trap in agent engineering? An agent can produce a correct final answer while failing silently along the execution path. To fix this, we have to shift to Trajectory Evaluation, scoring the full execution path across two main failure pillars: 1️⃣ Agent Task Success (Behavioral & Goal Alignment) • Hallucinations: Claiming it lacks tools it actually has, or hallucinating unperformed actions. • Instruction Following: Violating negative constraints, over-punting (asking unnecessary permission), or incomplete execution (stopping halfway). • Tool Output Handling: Failing to parse valid API return payloads. 2️⃣ Tool Use Quality (Syntactic & Schema Precision) • Parameter Errors: Passing string "50" instead of int 50, or swapping parameter mappings. • Selection & Syntax: Selecting the wrong tool or passing malformed JSON syntax. • Tool Hallucinations: Inventing fake function names or parameter keys. Vibe-checking final responses is like running unit tests that only check if your app exited with status code 0. In Part 2, I’ll share how to automate the solution using a 5-stage eval flywheel and evolutionary prompt engineering. - Everyone is focused on AI generating code. I think the more interesting problem is what happens after the code is written. Imagine an AI agent is asked to implement a new feature. It reads the repository. Understands the architecture. Writes the code. Runs the unit tests. Everything passes. Can it confidently say the task is complete? Not necessarily. Passing tests only tells us that certain assertions succeeded. It doesn't tell us whether: • the button appears where users expect it • navigation still works • a workflow was accidentally broken • the interface behaves correctly in a real browser This is why I think validation is becoming one of the most important building blocks of agentic workflows. Instead of relying only on their own reasoning, agents can use independent validation systems to answer a much better question: "Did the software actually behave as expected?" The workflow starts looking like this: Goal ↓ Reason ↓ Generate ↓ Validate ↓ Analyze failures ↓ Improve ↓ Validate again Notice something interesting. The validation system isn't replacing the agent. It's acting as an objective source of truth. Whether it's browser automation, end-to-end testing, visual regression testing, or tools like Bug0, Playwright, Cypress, Selenium and others, they all serve the same purpose: They help agents replace assumptions with evidence. As AI agents become better at building software, I think this feedback loop will matter just as much as the models themselves.

- If you look at how AI agents actually operate in production, it isn’t a straight line from prompt to response. It’s an ongoing, self-contained loop. Instead of thinking about an agent as just a clever chatbot, it helps to break down what’s actually happening into a continuous four-stage cycle: 1. Idea (The Intent) It starts with a high-level goal from the user. Rather than firing off an immediate text response, the agent uses planning techniques like ReAct to map out a strategy. It breaks down a broad request ("Analyze our competitor's pricing and send a summary") into a logical sequence of sub-tasks. 2. Action (Gears & Tools) Planning alone doesn't change anything in the real world. In this stage, the agent uses function calling to interact with external tools. It runs Python scripts, queries databases, searches the web, or hits third-party APIs. This is where the actual labor happens. 3. Checking (The Inspection) Once an action is executed, the agent inspects the output. Did the API return a 200 OK or a 500 error? Did the database query pull the right records? By evaluating the output against its short-term memory and context, it checks whether it actually accomplished the sub-goal. 4. Adjusting (The Self-Correction) This is what separates an agent from a standard automation script. When an action fails, a regular script just crashes. An agent reads the error message or stack trace, figures out what went wrong, tweaks its code or parameters, and loops back into the process to try again. The shift happening in software right now isn't just about AI generating text—it's about systems that can take an outcome, execute the work, inspect their own output, and fix their own mistakes along the way. If you're building or experimenting with agentic workflows right now, where in this cycle do your builds usually struggle? For most teams I talk to, steps 3 and 4 are the hardest to get right without the model getting stuck in a loop.

An agent grading its own work will eventually declare victory, not maliciously, but because victory is the cheapest path through the assignment. So we give it goals it can't grade for itself.
