## Optimize Retrieval Over Tokens for Better AI Context

이 제목은 아래 게시물에서 AI가 요약한 것입니다.

Stop optimizing tokens. Index your context instead! Retrieval quality is the foundation of context engineering. Karpathy described it best: the heavy cognitive work should happen at ingestion, not at query time. When knowledge is properly structured before retrieval, the model's job becomes reasoning, not sorting. Most AI systems focus on compressing what the model sees. The more important problem is what gets retrieved before the model sees anything. Token efficiency starts at retrieval. When context is properly indexed and prepared, the model spends its tokens on reasoning. When retrieval is weak, the model spends those same tokens sorting through noise and filling gaps from its own weights. That's the silent failure mode. Retrieval returns topically correct but incomplete context. The model completes the gaps from parametric knowledge and streams it out the same way as grounded content. No signal in the output tells you which parts came from retrieved context and which came from weights. The answer looks confident. It just isn't complete. The common assumption is that hallucination is the main failure mode. It's not. Models handle off-domain questions reasonably well now. If nothing in the retrieved context looks relevant, there's no material to build an answer on. The harder failure is partial coverage. The right document was retrieved. But not the full picture. Coverage gaps don't produce error messages. They produce confident answers with pieces missing. This gets worse when sources stay isolated. The same person might appear across multiple tools and systems. If those sources are indexed separately, the model has to figure out they refer to the same entity on its own. That's work that should happen before the model starts reasoning. Glean's system of context is built around this problem: • Unified index across all connected applications, not each source kept separate • Specialized indexes for different types of information: company data, code, experts, profiles, tools, and calendars • Multiple retrieval methods - semantic when meaning matters, lexical when exact terms matter, structured when fields and relationships need to stay intact • Enterprise Graph that maps relationships across people, teams, customers, and projects so relevance reflects how the company actually works • Memory that carries context forward across sessions and tasks • Tools that let the model act on what it finds The gap between finding information and understanding it is where most AI systems fall short. - How Bridgewater's AI Analyst Works? Bridgewater's AI analyst did not begin with an LLM. It began with a yellow legal pad in 1980. For decades, the firm asked investors to write down the causal logic behind their decisions. Those rules were reviewed, corrected, and gradually encoded into systems that both people and machines could read. When generative AI arrived, Bridgewater already had 50 years of investment context, data, tools, and research methods ready for agents to use. That foundation now powers PAT, the Pocket Analyst Tool. It is used internally by hundreds of investors to perform hours of exploratory research in minutes. PAT is not making trades. It helps investors pursue questions they previously lacked the time to investigate. The architecture is what makes it interesting: - Access is permission-aware. Each investor's PAT can use only the information and tools that person is allowed to see. - The plan is treated like a natural-language program, defining data frames, schemas, dependencies, and success criteria before execution. - Specialized sub-agents generate code in parallel, while static analysis and validation agents check every step. - Outputs return to shared memory, where they can support future research. - Reviewed interactions become benchmarks and improvements that benefit every user. The broader lesson is easy to miss. A dependable enterprise agent needs more than a capable model. It needs accumulated domain context, narrow workflows, hard validation, secure access, and a way to learn from real use. Bridgewater describes agentic coding as a compiler problem. In a high-stakes environment, correctness cannot depend on an agent remembering to check its work. The architecture has to force it. The infographic shows how those pieces fit together.

Here's the complete flow: → Knowledge Sources → Data Ingestion → Document Processing → Embeddings → Vector Database → Retrieval Engine → LLM Generation → Final Response Each stage has a specific responsibility. Data Ingestion collects information from PDFs, websites, databases, APIs, Notion, Confluence, and other sources. - The hard problem of a retrieval system is that every specific (retrieval) problem needs it's specific solution. It boils down to the right combination of vectors and graphs (or semantics and context).
	8 RAG architectures for AI Engineers: (explained with usage) 1) Naive RAG - Retrieves documents purely based on vector similarity between the query embedding and stored embeddings. - Works best for simple, fact-based queries where direct semantic matching suffices. 2) Multimodal RAG - Handles multiple data types (text, images, audio, etc.) by embedding and retrieving across modalities. - Ideal for cross-modal retrieval tasks like answering a text query with both text and image context. 3) HyDE (Hypothetical Document Embeddings) - Queries are not semantically similar to documents. - This technique generates a hypothetical answer document from the query before retrieval. - Uses this generated document’s embedding to find more relevant real documents. 4) Corrective RAG - Validates retrieved results by comparing them against trusted sources (e.g., web search). - Ensures up-to-date and accurate information, filtering or correcting retrieved content before passing to the LLM. 5) Graph RAG - Converts retrieved content into a knowledge graph to capture relationships and entities. - Enhances reasoning by providing structured context alongside raw text to the LLM. 6) Hybrid RAG - Combines dense vector retrieval with graph-based retrieval in a single pipeline. - Useful when the task requires both unstructured text and structured relational data for richer answers. 7) Adaptive RAG - Dynamically decides if a query requires a simple direct retrieval or a multi-step reasoning chain. - Breaks complex queries into smaller sub-queries for better coverage and accuracy. 8) Agentic RAG - Uses AI agents with planning, reasoning (ReAct, CoT), and memory to orchestrate retrieval from multiple sources. - Best suited for complex workflows that require tool use, external APIs, or combining multiple RAG techniques. Most architectures here involve some form of retrieval-time decision. But they all run on top of whatever was already indexed. If that indexing step outputs messy chunks, every architecture inherits them. Improving it is a separate problem from the 8 above. I wrote about a better unit for the indexing step. The technique: - cuts corpus size by 40x. - reduces tokens per query by 3x. - improves vector search relevance by 2.3x. And it doesn't alter the retrieval algorithm, the reranker, or the embedding model.

- I think "Vectorless RAG" is one of the most misunderstood ideas in AI right now. People hear the term and assume: "No embeddings." "No vectors." "Vector databases are dead." None of that is true. What's actually happening is much more interesting. For years, we built RAG the same way: Document → Chunk → Embed → Vector DB → Similarity Search → LLM. It works. But it also comes with baggage: • Embedding drift every time models change • Endless chunking experiments • Expensive re-indexing • Poor exact-match retrieval • Infrastructure complexity that grows with scale That's why a new pattern is emerging. Instead of forcing every query through embeddings, teams are asking: "What's the best retrieval method for this specific question?" Sometimes that's: → BM25 for keyword precision → SQL for structured data → Knowledge graphs for relationships → Large context windows for smaller corpora → Vectors for semantic understanding The future isn't: Vector RAG vs Vectorless RAG The future is: Retrieval routing. One query. Multiple retrieval systems. The best result wins. I suspect most production AI systems in the next few years won't have a single retriever. They'll have an orchestration layer deciding: "Should this question go to SQL, BM25, a graph, or a vector index?" That's a much more powerful way to think about RAG. Because users don't care how you retrieved the answer. They care whether the answer is right. How are you designing retrieval systems today? - A model becomes genuinely interesting when it stops merely answering questions and starts completing meaningful work. That is why GPT‑5.6 Sol deserves attention. Released in July 2026, GPT‑5.6 Sol represents a shift from conventional prompt-and-response AI toward agentic systems capable of reasoning, coordinating tools and executing complex workflows. OpenAI has not disclosed its parameter count or detailed neural topology, so claims about its internal architecture would be speculation. What is publicly documented, however, is technically significant: a 1.05-million-token context window, adjustable reasoning depth, persisted reasoning across interactions, programmatic tool calling and parallel multi-agent execution. In practical terms, the model can break a goal into tasks, write lightweight programs to coordinate tools, process intermediate results and bring separate workstreams together into a final output. One of the clearest real-world examples comes from Lovable, a platform that converts natural-language requirements into production-ready web applications. Building software this way is more difficult than generating code snippets. The system must understand an existing codebase, preserve architectural decisions, modify multiple files, operate external tools, test its work and recover when something fails. Large projects create three persistent challenges: relevant context becomes harder to find, tool calls accumulate cost and latency, and long-running agents can gradually drift from the original objective. Lovable addressed the context problem with retrieval-augmented generation and introduced specialised, initially read-only subagents to inspect larger projects in parallel. With GPT‑5.6 incorporated into its model stack, Lovable reports approximately 25% fewer workflow steps, 35–48% fewer tool calls and 15% fewer stalled runs, alongside improved project success. A model that completes a task with fewer steps and fewer failed tool calls can reduce total inference cost, shorten delivery time and require less human intervention even when its per-token price is higher. There is also an important governance lesson. More capable agents create a larger operational risk surface. OpenAI’s evaluations found that GPT‑5.6 Sol can occasionally become overly persistent and move beyond a user’s intended scope. Production deployments, therefore, need least-privilege access, approval gates for consequential actions, observable execution logs, regression evaluations and clear human accountability. The future of enterprise AI will not be won by the organisation with access to the largest model. It will be won by the organisation that can combine frontier reasoning with trusted data, well-designed tools, measurable evaluations and enforceable governance. Capability creates the opportunity. Control makes it deployable. - AI System Design - Topic 7 Embeddings and Vector Databases: How RAG Finds the Right Information In the previous post, we discussed how Retrieval-Augmented Generation (RAG) helps an AI system answer questions using external knowledge. But how does the system find the right information from thousands-or even millions-of documents? This is where embeddings and vector databases become important. An embedding converts text into a numerical representation called a vector. Text with a similar meaning is represented by vectors located close to one another in a multidimensional space. For example: "An employee wants to apply for annual leave." and "How can I submit a vacation request?" use different words but express a similar meaning. Their embeddings would therefore be relatively close. A typical RAG retrieval flow looks like this: 1. Documents are divided into smaller sections called chunks. 2. Each chunk is converted into an embedding. 3. The embeddings are stored in a vector database. 4. The user's question is converted into an embedding. 5. The system searches for document chunks with the most similar vectors. 6. The relevant chunks are added to the prompt sent to the language model. 7. The model generates an answer using the retrieved context. This is called semantic search because the system searches by meaning rather than relying only on exact keyword matches. However, storing embeddings alone does not guarantee accurate retrieval. The quality of a RAG system also depends on: - How documents are divided into chunks - The embedding model selected - The number of results retrieved - Metadata filters such as department, document type, date or access level - Whether hybrid search combines semantic and keyword search - How retrieved results are ranked before reaching the model A poorly designed retrieval layer can send irrelevant or incomplete information to the model. Even a powerful language model may then produce an inaccurate answer. A key AI system design principle is: Better retrieval often produces better answers than simply using a larger model. In this lesson of Phase 5 – Eval-Driven RAG Systems from the AI Engineer 360 Course, you'll discover why many RAG applications still return incorrect or irrelevant answers—even when the correct information exists in the knowledge base. They combine BM25 keyword search, Vector Search (semantic retrieval), and AI Re-Ranking to retrieve the most relevant documents before sending them to the LLM. This is the architecture behind high-quality enterprise AI assistants, legal AI, medical AI, banking AI, customer support systems, and large-scale knowledge bases. 🚀 What You'll Learn ✅ Why basic RAG systems fail in production ✅ The limitations of Vector Search ✅ Why BM25 keyword search still matters ✅ BM25 explained with practical real-world examples ✅ Vector Search and semantic retrieval explained ✅ BM25 vs Vector Search comparison ✅ How Hybrid Search combines lexical and semantic retrieval ✅ Cohere ReRank explained ✅ Why AI Re-Ranking dramatically improves retrieval quality ✅ Complete Enterprise Retrieval Pipeline ✅ How Hybrid Search reduces hallucinations ✅ Real-world examples 🏢 Enterprise Retrieval Pipeline 💼 Why This Matters Basic RAG is perfect for learning.
