# Persistent Knowledge Graph for Codebases with Codebase-MCP | Sumanth P님이 토픽에 대해 올림

## Persistent Knowledge Graph for Codebases with Codebase-MCP

이 제목은 아래 게시물에서 AI가 요약한 것입니다.

Give your AI agent a persistent knowledge graph of your entire codebase! Most AI coding agents read files when you point them at something. They have no structural understanding of your codebase, no idea what calls what, and they start from scratch every session. codebase-memory-mcp builds a persistent knowledge graph of your entire codebase that your agent can query in under 1ms. An average repo indexes in milliseconds. The Linux kernel, 28 million lines across 75,000 files, takes 3 minutes. Five structural queries run at around 3,400 tokens compared to 412,000 for file-by-file grep exploration. What it gives your agent: • 158 languages via vendored tree-sitter grammars compiled into a single static binary, zero dependencies • Hybrid LSP semantic type resolution for Python, TypeScript, JavaScript, PHP, C#, Go, C, C++, Java, Kotlin, Rust, and Perl, building call graphs that understand inheritance, generics, and cross-file imports • 15 MCP tools covering search, trace, architecture overview, impact analysis, dead code detection, Cypher queries, and cross-service HTTP linking • Auto-sync via a background watcher that detects file changes and re-indexes automatically • Team-shared graph artifact via a compressed SQLite snapshot you commit to the repo so teammates skip the reindex • Built-in 3D graph visualization • Configures itself for Claude Code, Codex CLI, Gemini CLI, Zed, OpenCode, Aider, KiloCode, VS Code, OpenClaw, Kiro, and 33 more agent surfaces with one install command 100% open source. 	Everyone talks about AI rewriting code. Almost no one talks about how you prove it actually works. So I tested it end to end — on a real app, documented every step. I took Kanboard (a popular open-source project stuck on PHP 7.4) and did a full rewrite to Python — FastAPI + SQLModel, same JSON-RPC API, strangler pattern. With no official Python version to grade against, a black-box behavioral test harness became my single source of truth. Then I let two tools play to their strengths: 🔹 Yardstick first — built a behavioral test harness with Kiro before touching the rewrite. 🔹 Transform at scale — ran the bulk PHP→Python rewrite with AWS Transform Custom, using the harness as its validation gate. Continual learning kicked in between runs. 🔹 Last mile — Kiro finished the features the harness couldn't grade, verified with a side-by-side shadow run. Honest coverage, not a suspiciously perfect number. The lesson? The magic isn't one tool — it's the pairing. Transform does the heavy, at-scale work. Kiro builds the safety net and closes the gap. Together they turn "trust me, the AI did it" into "here's the proof." - So we decided to build the thing and see if the idea actually held up. FlowMCP is an attempt to build MCPs around reusable workflows instead of sprawling tool surfaces. The model still decides what needs to happen, selects the correct flow and supplies the required inputs. But once the workflow starts, the known steps are handled by deterministic software instead of asking the model to figure out the same execution path every time. That is the theory anyway. I still do not know if this is the answer, or if I spent a day over-engineering something that could have been a Python script. So I tested it. I ran models of different sizes against several MCP configurations, including raw tool surfaces, tool search, written recipes and prebuilt flows. The goal was not to prove FlowMCP was amazing. It was to test the original claim: Does reducing the model’s tool-selection and execution burden make the workflow more reliable? The benchmark report is here: [https://lnkd.in/epHneHzu](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Flnkd%2Ein%2FepHneHzu&urlhash=kBDC&trk=public_post-text) The report itself was synthesized with AI. The tests were selected and run by me, the outputs were reviewed by me, and I decided which conclusions the results actually supported. The model was just extremely useful for turning all of that into something readable. The early results are interesting. Now I need to see whether it can survive real workflows, messy APIs and failure paths that were not designed for a benchmark. Because that is where this either becomes useful or falls apart.

Why this approach works: - Precision: The script parses diff headers to ensure the AI only comments on lines you actually changed. This prevents hallucinations. - Control: You define the rules. You can instruct the AI to focus on security, UI, or logic by changing the prompt. - Automation: If the AI finds issues, it marks the PR as "Request Changes." - AI Agents typically operate on a framework called ReAct (Reason + Act): Reason (Thought): The LLM analyzes the user's request and decides what needs to be done. Act (Tool Use): The agent triggers an external tool. It might run a Python script, search the web, query an API, or write to a file. Observe: The agent looks at the output of the tool it just used. If the task isn't finished, it loops back to the "Reason" step to decide what to do next. For example, if you ask an agent, "What is the current price of Apple stock, and if I bought 10 shares today, how much would that be in Egyptian Pounds?", the agent will reason that it first needs to trigger a web search tool to find the stock price, then trigger a calculator tool to multiply by 10, then trigger a currency conversion tool to get EGP, and finally return the result to you.
