- Your AI agents don't need to re-read the whole conversation every single time. Most LLM "memory" today is just an illusion: replay the entire chat history on every turn. Costs grow linearly, context windows choke, and it gets worse the moment you add a second agent. A recent deep-dive on the [Neo4j](https://www.linkedin.com/company/neo4j?trk=public_post-text) blog shows a different approach — pairing a semantic memory engine ([Semvec](https://de.linkedin.com/company/semvec?trk=public_post-text)) with Neo4j as the single source of truth for both domain knowledge and conversation state. The results, benchmarked on LOCOMO (the same long-term memory test used for mem0, Zep, and Letta): ~8× fewer tokens per call vs. full-context replay (~87% reduction) ~8× faster ingest, with zero LLM calls needed at ingest time Quality on par with mem0 — without the generative overhead One graph for everything: patients, sessions, drift events, and audit trails — joined in a single Cypher query The clever part: it doesn't just compress a single agent's memory. It scales to entire teams of agents — shared "cluster" memory, cross-team drift detection, shift handovers with checksummed exports, even consensus voting when multiple agents disagree. If you're building multi-agent systems and watching your token bill grow with every turn, this is worth a read. - Most AI agents are blind. They can read, write, and search — but they can't watch a video and tell you what happened. They also can't look at their own visual output and check if it's correct. Watch Skill is an open-source MCP server (MIT license) that addresses both gaps. It gives AI agents the ability to watch video from over 1,800 sites, live streams, and local files — then build a searchable index and answer questions about what they saw. It exposes 13 tools across MCP, CLI, and REST with OpenAPI, all backed by a single Python engine. What sets it apart is THE LOOP: a capture→critique→fix→re-verify cycle that lets agents verify their own visual output. An agent generates a checkout page. THE LOOP captures a screenshot, critiques it against natural-language criteria, and if something is wrong — like "TOTAL: $NaN" — it tells the agent what to fix. The cycle repeats until the output is correct, producing before-and-after proof images. The answer engine is equally deliberate. It uses a confidence-and-escalation architecture: cheap CPU operations first (keyword + vector search), then denser frame sampling, then targeted OCR. Only as a last resort does it call a vision model. And if the video genuinely doesn't contain the answer, the system has an "honest floor" — it says so rather than fabricating. Privacy is enforced by design, not policy. Transcription, OCR, and embeddings all run locally. Automated tests verify this invariant. For teams handling sensitive video, this removes the risk of data ever leaving the machine. The project is young and transparent about its limitations: setup requires Python 3.11+ and several binary dependencies, vector search needs scaling beyond ~10K segments, and retrieval quality claims are self-reported without independent benchmarks yet. The compatibility matrix is honestly graded — only Claude Code and REST/HTTP are machine-tested end-to-end. It's a pragmatic, well-architected tool that addresses a real gap in the agent ecosystem. What visual verification challenges are you encountering with AI agents? I'd be curious to hear how teams are handling this today. - How would I design an LLM routing system for a Python-based AI agent? I would avoid sending every request to the same model. Instead, I would build a simple routing layer with five steps: 1. Analyze the request First, classify the user’s intent and estimate the complexity of the task. The router could return a structured result such as: { "route": "coding", "confidence": 0.93, "needs\_retrieval": false } For obvious requests, I would use deterministic rules. For ambiguous ones, I would use a small and fast LLM as a classifier. 2. Route the request The routing table could look like this: Coding: reasoning or coding-focused model Content writing: model optimized for writing and tone Summarization: faster and lower-cost model General Q&A: general-purpose model Company or domain questions: RAG pipeline with access to trusted sources 3. Add confidence thresholds If the router has high confidence, the request goes directly to the selected model. If confidence is low, the system can: send the request to a stronger general model; ask the user for clarification; or use a predefined fallback route. 4. Apply shared controls Regardless of the selected model, every route should use the same authentication, safety rules, logging, timeout, retry, and output-validation mechanisms. 5. Evaluate the routing decisions I would monitor: routing accuracy; response quality; latency; cost per request; fallback frequency; and user feedback. The objective is not to find one model that is best at everything. It is to select the most appropriate model for each request while maintaining the required quality, reliability, and cost. Would you build this router with rules, an LLM classifier, or a hybrid approach?
