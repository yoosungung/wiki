## Cloudflare Open-Sources AI Productivity Workspace Cloudflare OS

이 제목은 아래 게시물에서 AI가 요약한 것입니다.

Cloudflare open-sourced their own internal AI OS! Cloudflare OS is an AI productivity workspace originally built for internal use at Cloudflare. A large portion of their workforce - engineering, sales, and everything in between - uses it every day. They're open-sourcing it so others can fork and customize it as their own company OS. The core idea is a departure from how cloud software has worked for the past 25 years. When you create a slide deck in Cloudflare OS, you're not connecting to a shared SaaS app running on someone else's server. The system creates a private instance of slide deck software just for you, running in its own sandbox. They call these Gadgets. This has two direct consequences. First, a security bug in the slide deck app can't leak your slides to anyone else because your instance is completely isolated. Second, if the app is missing a feature you need, you can ask the agent to add it. And because you're running your own copy, it's safe to do so. The security model underneath this is called Gatekeepers. Each external resource connection gets a Gatekeeper that handles authorization, enforces narrow access to only what you intended, and logs every action for review. The genuinely interesting part is how Gatekeepers handle human approval. Most agent setups stop and wait for the human to approve each action before continuing - which is why people often end up using "dangerously-skip-permissions." Gatekeepers simulate the action locally instead, let the agent keep working, queue the real action, and let the human approve or reject in bulk later when convenient. Key capabilities: • Gadgets: private per-user instances of every app, sandboxed and AI-modifiable • Gatekeepers: async human-in-the-loop approval without blocking agent progress • Blueprints: shareable app templates where each user runs their own copy • Built-in coding agent that builds, tests, and debugs Gadgets • Real-time multiplayer collaboration via Durable Objects • Capability-based security - agents get access to nothing by default • Runs on Cloudflare Workers or self-hosted on workerd I've shared the link in the replies!

- Cloudflare OS: A Runtime and Security Model for Enterprise AI Agents Cloudflare has open-sourced Cloudflare OS, the AI productivity environment built for internal use across engineering, sales and other teams. The August 2026 release is version 2, a full rewrite still labelled early access. This is not another chat interface with connectors. Each user-created application is a private “Gadget” with its own state, code and permissions. A Gadget can be modified, shared, or published as a Blueprint for another user to create an isolated copy. The runtime is built on Cloudflare Workers. Each workspace is a Durable Object, each Gadget runs in a Dynamic Worker Facet, and external services are mediated through Gatekeepers. It can also run on the open-source workerd runtime, though self-hosting guidance is incomplete. Security is capability-based rather than ambient. Agents and Gadgets start with no access to external systems. A GitHub repository, Google document or other resource must be explicitly introduced. The Gatekeeper handles OAuth, narrows access to the intended resource, records activity and mediates side-effecting actions. A key control is deferred approval. A Gatekeeper can simulate an action locally, let the agent continue with simulated results, and queue the real actions for later approval or rejection. That reduces pressure to use unsafe auto-approve modes while preserving human control. Isolation exists on both sides. The gadget server code has no direct internet access unless a resource is explicitly bound. Client code runs in a sandboxed iframe with CSP controls and communicates with the server through Cap’n Web RPC. The agent uses Code Mode: it writes and executes code to perform tasks, build Gadgets, call APIs, test applications, and debug failures. Every Gadget exposes an agent-friendly Cap’n Web interface, so AI collaboration is part of the application model rather than added later. Cloudflare’s OS analogy is concrete: workshop-backend acts like the kernel, Gatekeepers like device drivers, Gadgets like processes, and Blueprints like executables. What stands out is where the trust boundary sits. Gadgets cannot reach the internet by default, agents do not inherit broad connector access, side-effecting actions are mediated, and human approval does not have to block execution. That is materially safer than giving an LLM broad access to tools and relying on prompt instructions to contain it. - We gave a "digital employee" its own Microsoft 365 Copilot license. Here's what we found (August 2026). This week at SYNTAX, we ran an unconventional experiment: creating "Robot IA 1," an autonomous agent with its own identity in Microsoft Entra Agent ID — not a generic service account, but a real "digital employee" with its own mailbox, its own OneDrive, and, most importantly, its own Copilot license. The goal wasn't for it to "act on behalf of" a human. It was to give it its own identity, its own designated owner (sponsor), and the ability to reason with AI autonomously before notifying its supervisor. We documented 3 technical findings that, as far as we can tell, aren't covered with this level of detail in Microsoft's public documentation: 1️⃣ The standard "application" token, presented in official documentation as the normal way for an autonomous agent to call Microsoft Graph, does NOT work for sending mail from the agent's own mailbox. It fails with a 401 and an empty body, no matter how Exchange RBAC is configured. We confirmed this against a publicly documented official Microsoft support case (35 days of investigation), with a written conclusion: Exchange's data plane rejects this identity type before any permission is even evaluated. The real fix: an "Agent User token," a 3-step impersonation flow that isn't clearly documented as the recommended path. 2️⃣ OneDrive doesn't auto-provision for an identity that never signs in interactively. Since the agent has no password or MFA by design, it never triggers the "first visit" event that normally creates the site. The real, documented fix: provision it manually, once. 3️⃣ The Copilot Chat API rejects the agent at its internal backend, even with the license assigned, the correct delegated permissions, and a valid token. Our strongest hypothesis: a user's Copilot profile gets activated the first time they sign in interactively — something a fully autonomous agent can never do. Unlike #2, there's no known manual provisioning workaround here (yet). The honest conclusion: we got the agent sending mail and writing audit logs 100% autonomously — that part works and is repeatable. But the core goal of the project — having it reason using its own Copilot license — we did not achieve. That's why we removed the license: no point paying for something the platform won't let you actually use today. Can this be continued? Yes, but it would be a different project: giving this agent "intelligence" via pay-as-you-go (Azure OpenAI or the Work IQ API) instead of a per-seat Copilot license. Different architecture, different cost model — and probably the right path today for autonomous AI reasoning in Microsoft 365. Entra Agent ID is a fascinating, very new surface. But as of August 2026, some pieces — especially around Copilot — aren't production-ready for non-interactive identities.
