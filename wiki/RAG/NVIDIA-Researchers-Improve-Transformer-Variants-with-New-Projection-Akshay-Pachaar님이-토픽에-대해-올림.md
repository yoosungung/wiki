# NVIDIA Researchers Improve Transformer Variants with New Projection | Akshay Pachaar님이 토픽에 대해 올림

NVIDIA researchers built a new transformer variant. One small change to the layers made: - decoding 1.7x faster - long-reasoning accuracy up 6.5 points Every attention layer computes Q, K, and V. NVIDIA's tweak adds a fourth projection that predicts what the next layer will need. To see why, look at long-context inference today. Sparse attention scores the KV cache in blocks, keeps the top-k, and attends only to those. That cuts compute and bandwidth, but two problems remain. > First, the KV cache still grows with every generated token. At 100K+ context it no longer fits in GPU memory and gets offloaded to CPU RAM. Every layer must then copy its selected blocks back, and the GPU sits idle during that copy, at every layer of every decode step. > Second, the selection step itself is not free. Standard selectors score every candidate block with every query head in a GQA group (grouped-query attention, where several query heads share one KV head), then softmax and sum across the group. Decode attention is cheap with one query token, but this selection cost grows with context length. Both problems trace back to the same design, i.e., the attention query drives the block selection. Q only exists once its layer is already running, so it is too late to fetch anything early, and the query drags its multi-head layout into selection. A recent paper from NVIDIA and MIT called SparDA breaks this coupling. Each layer now emits four projections instead of three: ↳ Q, K, V, and a Forecast. The Forecast from layer L predicts which KV blocks layer L+1 will need, and layer L+1's own query then attends over those blocks. Since the next layer's block set is known while the current layer is still computing, the runtime fetches those blocks on a separate CUDA stream, overlapping the copy with compute. And since the Forecast is separate from the query, it needs one head per GQA group, which removes the per-query-head scoring loop and skips the softmax entirely. DeepSeek did something similar in DSA, where a small indexer picks important tokens. SparDA applies it to blocks and adds the prefetch angle. The cost is small. The Forecast adds 33.5M parameters on an 8B model (0.41%), and only those projections are trained, using a KL loss that matches the original selector's block distribution. On MiniCPM4.1-8B and NOSA-8B, accuracy matches or beats the sparse baseline, with NOSA-8B gaining +6.5 on long reasoning. Prefill runs up to 1.25x faster and decode up to 1.7x faster than the sparse offload baseline. There's one more benefit. Because prefetch hides the offload cost, most of the KV cache can live in CPU RAM, and the freed GPU memory fits much bigger batches, pushing decode throughput up to 5.3x over the non-offload sparse baseline. That said, the lookahead only pays off during decode with CPU offload. During prefill all keys already live on the GPU, so the gain comes purely from cheaper selection. ## 관련성이 더 높은 업데이트

- 106% of cuBLAS. At first glance, that sounds impossible. How can a custom GEMM kernel outperform NVIDIA's highly optimized cuBLAS library? The answer isn't a magical optimization. It's the cumulative effect of exploiting every major architectural feature introduced in NVIDIA Blackwell, while redesigning the kernel around the hardware instead of treating the GPU like a faster CPU. The optimization journey starts with a conventional BF16 Tensor Core GEMM using Tensor Memory Accelerator (TMA) to move tiles from HBM into shared memory before Tensor Cores perform matrix multiply-accumulate operations. This baseline reaches only about 40% of cuBLAS, not because Tensor Cores are slow, but because they spend much of their time waiting for memory and synchronization. The first breakthrough comes from 2-CTA MMA. Previous architectures restricted matrix multiply operations to a single Cooperative Thread Array (CTA). Blackwell's 5th-generation Tensor Cores allow two CTAs to cooperate on one larger MMA instruction. Instead of performing two independent 128×256 operations, two neighboring CTAs execute one 256×256 operation. This removes redundant memory loads, increases arithmetic intensity from roughly 85 FLOPs/byte to 128 FLOPs/byte, and dramatically improves data reuse. The GPU performs more computation for every byte fetched from memory. The kernel then adopts warp specialization. Rather than assigning identical responsibilities to every warp, different warps become specialists. Producer warps exclusively issue TMA memory transfers, consumer warps issue MMA instructions, and separate epilogue warps handle output writes. This separation allows memory movement, Tensor Core execution, and result storage to overlap continuously, increasing overall streaming multiprocessor utilization. Another major improvement is the transition to persistent kernels. Traditional GEMM launches a new CUDA kernel for every output tile, repeatedly paying launch overhead and initialization costs. Persistent kernels launch only enough thread blocks to occupy the GPU's Streaming Multiprocessors, then repeatedly fetch new work internally. Prologue costs are paid once, while Tensor Memory allocation and synchronization structures remain active throughout execution, keeping both Tensor Cores and TMA engines busy almost continuously. The final result is remarkable: a custom Blackwell GEMM kernel that reaches 106% of cuBLAS for selected workloads. More importantly, it demonstrates that future AI performance is no longer driven solely by faster Tensor Cores. The largest gains now come from understanding memory hierarchy, scheduling, synchronization, asynchronous execution, cache locality, persistent execution models, and hardware-aware software design. In the Blackwell era, optimizing AI workloads is no longer just CUDA programming. It is computer architecture engineering in software.

- I reproduced an NVIDIA paper "Low-Rank Dependence Decomposition via Accelerated Symmetric Non-negative Matrix Factorization" (Ghita et al., arXiv:2607.24518). The idea: take an n×n dependence matrix between financial instruments and factorize it as S ≈ H·Hᵀ with H non-negative. The columns of H become interpretable risk factors; each row is a soft cluster assignment of one instrument. They study two inputs - the familiar correlation matrix, and the tail pairwise dependence matrix (TPDM) from Extreme Value Theory, which captures co-crash structure that correlation misses entirely. The trick that makes it a GPU problem: a naive implementation of ‖S − HHᵀ‖² materializes n×n intermediates (~20n² bytes). The paper's trace-identity reformulation eliminates all of them, cutting memory to ~4n² bytes and reducing every solver iteration to two dense cuBLAS matrix products. That one algebraic identity is why they reach n ≈ 100,000 on a single GPU. I reimplemented it in CuPy on an RTX PRO 5000 Blackwell laptop GPU and ran their benchmark: a planted block factor model, both matrix types, their AdaGrad solver against classical multiplicative updates, and their strict three-part convergence gate. Results from my machine: → A converged factorization of a 4,000-instrument universe: 1–3 seconds. → The planted factor structure recovered exactly from the permuted matrix — purity 1.000 on correlation inputs. → Throughput sweep, 200 iterations: GPU 1.2× faster than CPU at n=1,000, 4.8× at n=2,000, 11.5× at n=4,000, 29.5× at n=8,000. The CPU curve grows as O(n²k); the GPU curve barely moves. → At ~4n² bytes, a 24 GB card clears roughly 70,000 instruments, full-universe scale for an equity risk model. Why it matters for quant work: factor extraction over an entire book stops being an overnight batch job. At seconds per solve, re-estimating your factor structure becomes something you can do intraday, on hardware that fits in a backpack. Honest caveats: benchmark matrices are synthetic (the paper's own construction), the AdaGrad step size needed re-tuning on my benchmark (η=0.05 vs their 2.0 - step size is spectrum-dependent), and my demo sizes sit below the scale where the paper shows multiplicative updates start failing. Educational reproduction, not investment advice. Full experiment report with methodology, tables, and figures in the comments/attached. - Teams open nvidia-smi, see 95% GPU utilization, and assume the GPU is working hard for them. It isn't. Not always. GPU Utilization %: tells you a kernel is running. Says nothing about whether that kernel is doing useful work. Tensor Core Utilization: tells you if you're actually using the matrix units the GPU was built for. Memory Bandwidth Utilization: tells you if you're compute-bound or memory-bound. The issue: You can sit at 95% GPU utilization while your tensor cores are nearly idle and the real bottleneck is memory movement. Why: Small batch sizes underuse tensor cores. The GPU looks "busy" but is doing near-scalar work. Attention layers are frequently memory-bandwidth bound, not compute bound. Kernel launch overhead between small ops keeps the GPU "active" without adding FLOPs. Real scenario: Dashboard shows 92% GPU utilization. Inference is still slow. You profile with Nsight and find 60% of time is spent moving KV cache in and out of memory, not computing attention. The GPU is busy waiting, not busy computing. Solution: Don't trust GPU utilization % alone. Profile with Nsight Systems / Compute. Check tensor core utilization specifically. Fix batching. Too small wastes tensor cores, too large blows out the KV cache. Fuse kernels where you can to cut launch overhead. Move memory-bound ops (long-context attention) to paged KV cache / FlashAttention-style kernels. Most teams optimize the number on the dashboard. Not the number that's actually costing them. This is the exact loop we run before touching a single line of model code: profile first, guess never.
