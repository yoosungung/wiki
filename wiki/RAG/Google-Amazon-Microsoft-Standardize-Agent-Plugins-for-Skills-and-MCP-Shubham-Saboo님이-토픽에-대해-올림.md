## Google Amazon Microsoft Standardize Agent Plugins for Skills and MCP

이 제목은 아래 게시물에서 AI가 요약한 것입니다.

Google, OpenAI, Amazon, Microsoft, Cursor, and Vercel just standardized how Skills and MCP gets packaged as an Agent Plugin 🔥 It's called Agent Plugins 1.0.0. An open, vendor-neutral spec for packaging Skills and MCP servers together. Build a plugin once. Run it in Claude Code, Codex, Cursor, or Antigravity. It fixes a problem every skill author has hit. You write a skill. You write an MCP server to go with it. Then you ship it to a second client and the wrapper breaks. Different directory layout, different manifest, different MCP config shape. You fork the package and watch two identical copies drift apart. Agent Plugins standardizes the wrapper. A plugin is just a directory: a two-line [plugin.json](http://plugin.json/?trk=public_post-text), skills in skills/, MCP servers in [mcp.json](http://mcp.json/?trk=public_post-text) with explicit transport types, and a namespaced folder for client-specific extras that other clients simply ignore. Packaging is one layer in a bigger stack that's forming: • Find it: Agentic Resource Discovery (ARD), an open protocol that lets a client ask "what's available for this task?" and get back matching resources • Describe it: AI Catalog, the entry format ARD indexes, with plugins proposed as a known type • Package it: Agent Plugins. One directory, fixed locations, portable across clients • Run it: MCP and Agent Skills, the execution contracts that were already portable Every layer is independently adoptable. You can publish a plugin with no catalog entry, or run skills with no plugin at all. Google support is live today. Agents CLI ships Google's agent-building skills as a portable plugin, and Data Agent Kit brings BigQuery, Spanner, and Cloud SQL skills and MCP servers to any compatible client. The agent stack is settling into layers the same way the web did. Discovery, description, packaging, execution, each one swappable. Link to the full blog in the comments.

The layer that's still unsolved in this stack is trust at the discovery step. We run a catalog of ~50,000 MCP servers, and the hard operational problem isn't packaging — it's that a big share of entries are duplicates or abandoned copies of official servers, and a client asking ARD "what's available for this task" can't tell them apart. Packaging standardizes the wrapper; discovery still needs verification signals (domain ownership, security audit, uptime history) baked into the catalog entry itself, or agents will confidently install the wrong thing. - What is Function calling & MCP for LLMs? (explained with visuals and code) Before MCPs became popular, AI workflows relied on traditional Function Calling for tool access. Now, MCP is standardizing it for Agents/LLMs. The visual below explains how Function Calling and MCP work under the hood. Today, let's learn: - Function calling by building custom tools for Agents. - How MCPs help by building a local MCP client with mcp-use and using tools from Browserbase MCP server. In Function Calling: - The LLM receives a prompt. - The LLM decides the tool. - The programmer implements a procedure to accept a tool call request from the LLM and prepare a function call. The tool call request is found in the LLM's response when you prompt it. - A backend service executes the tool. This Function Calling takes place within our stack: - We host the tool. - We implement a logic to determine the tool to invoke and its parameters. - We execute it. So Function Calling requires us to wire everything manually. MCP simplifies this! Instead of hard-wiring tools, MCP: - Standardizes defining, hosting, and exposing tools. - Makes it easy to discover tools, understand schemas, and use them. - Demands approval before invoking them. - Detaches implementation from consumption. For instance, whenever you integrate an MCP server, you never write a line of Python code to integrate the tools. Instead, you just integrate the MCP server and everything beyond this follows a standard protocol handled by the MCP client and the LLM: - They identify the MCP tool. - They prepare the input argument. - They invoke the tool. - They use the tool’s output to generate a response. Everything happens through a standard (but abstracted) protocol. So here’s the key point: MCP and Function Calling are not in conflict. They’re two sides of the same workflow. - Function Calling helps an LLM decide what it wants to do. - MCP ensures that tools are reliably available, discoverable, and executable, without you needing to custom-integrate everything. For example, an agent might say, “I need to search the web,” using function calling. That request can be routed through MCP to select from available web search tools, invoke the correct one, and return the result. Check the workflow in the diagram below. - Serverless and statelessness "Serverless" is a marketing word. There are absolutely servers. You just don't manage them. That part most people know. The part that actually bites is the second one, and almost nobody states the mechanism correctly. People say serverless functions are "stateless" like it's a rule you're asked to follow, a best practice you could bend. It isn't. It's mechanical. Between two invocations of your function, the execution environment is destroyed. The process is torn down, its memory wiped. The next call may spin up a brand new environment on different hardware with no trace of the last one. Any variable you were holding in memory is gone, not by policy, but because the container that held it no longer exists. That's why state has to live in an external store. Not because a style guide says so. Because there is no in-memory left to store it in. This flips how you pass data around. In a normal agent crew, handing research to the copywriter is just a variable in memory. Go serverless and those two functions may run on different machines, and the research function's memory is guaranteed gone the instant it finishes. So the research output has to be written somewhere durable, a database, an object store, a queue payload, and the copywriter reads it back when it starts. State moves from implicit-in-memory to explicit-in-storage. The other tax is cold starts. The first request after an idle period is slow while the environment spins up. For a background job nobody is waiting on, irrelevant. For a user facing API, a dealbreaker. Serverless doesn't make distribution optional. It makes "no shared memory" unavoidable, and forces you to be explicit about every piece of state you were quietly keeping in RAM. If your function can't hold anything in memory between calls, where does the state it needs actually live, and is that store as reliable as the function assumes?

- 🤔 MCP vs API. Everyone is talking about MCP. But nobody explains how it's actually different from a regular API. Let me fix that in 2 minutes. 👇 ━━━━━━━━━━ 𝗙𝗶𝗿𝘀𝘁 — 𝘄𝗵𝗮𝘁 𝗶𝘀 𝗮𝗻 𝗔𝗣𝗜? An API is a set of rules that lets one system talk to another. A payment API lets an e-commerce site process cards. A weather API lets an app show today's forecast. A REST API sends an HTTP request → gets a JSON response. Simple. Powerful. Been around for decades. ✅ ━━━━━━━━━━ 𝗧𝗵𝗲𝗻 — 𝘄𝗵𝗮𝘁 𝗶𝘀 𝗠𝗖𝗣? Model Context Protocol. Think of it as a USB-C port for AI applications. 🔌 Just like USB-C lets you plug in a monitor, hard drive, or charger using ONE standard — MCP lets AI agents connect to databases, file systems, email servers, GitHub — using ONE standard. ━━━━━━━━━━ 𝗦𝗮𝗺𝗲 𝗯𝘂𝘁 𝗱𝗶𝗳𝗳𝗲𝗿𝗲𝗻𝘁. 𝗛𝗲𝗿𝗲'𝘀 𝘄𝗵𝗮𝘁 𝗰𝗵𝗮𝗻𝗴𝗲𝘀: 🔴 𝗔𝗣𝗜 — General purpose Built for any system talking to any other system. Not designed with AI in mind. Each API is unique — different endpoints, formats, auth. 5 APIs = 5 different adapters to build. 🟢 𝗠𝗖𝗣 — Purpose built for AI Designed specifically for LLMs and AI agents. Every MCP server speaks the SAME protocol. 5 MCP servers = same call every time. Build once. Integrate many. 🎯 ━━━━━━━━━━ 🔥 𝗠𝗖𝗣'𝘀 𝗯𝗶𝗴𝗴𝗲𝘀𝘁 𝘀𝘂𝗽𝗲𝗿𝗽𝗼𝘄𝗲𝗿 — 𝗗𝘆𝗻𝗮𝗺𝗶𝗰 𝗗𝗶𝘀𝗰𝗼𝘃𝗲𝗿𝘆 With a REST API — if the API changes, a developer must update the client manually. With MCP — the AI agent simply asks the server: "Hey, what can you do?" The server returns a live list of all capabilities. Agent adapts automatically. No code changes. No redeployment. 🚀 ━━━━━━━━━━ 💡 𝗛𝗲𝗿𝗲'𝘀 𝘁𝗵𝗲 𝘁𝘄𝗶𝘀𝘁 𝗻𝗼𝗯𝗼𝗱𝘆 𝗺𝗲𝗻𝘁𝗶𝗼𝗻𝘀: Most MCP servers STILL use traditional APIs under the hood. The GitHub MCP server exposes a tool called repository/list. - Agent Plugins 1.0.0 is now available: an open source, vendor-neutral specification that provides a common packaging format for AI agent extensions. Authors can package an extension once and ship it to compatible clients, including Kiro, Claude Code, VS Code, and Cursor. Version 1.0 deliberately focuses on two widely adopted components: Agent Skills and MCP servers. It defines the portable foundation while leaving installation, distribution, and user experience to individual clients. AWS is a founding member of the Technical Steering Committee alongside Cursor, Microsoft, OpenAI, and Vercel. AWS is supporting the specification through AWS Agent Toolkit and Kiro Powers. Model choice gives developers flexibility in which AI they use. Portable extensions provide similar flexibility in which tools their AI can use. - Everyone's arguing about MCP vs APIs. Here's the take that actually made it click for me. Quick myth-bust first: MCP doesn't replace APIs. It sits in front of them. Here's the real problem MCP solves 👇 Say your app talks to 10 services — Slack, Gmail, Jira, Notion, your own DB, etc. You hand-write the auth, error handling, and retries for all 10. Now build a second AI app that needs the same 10 services. You write all 10 integrations again. Two apps × 10 services = 20 piles of integration code to maintain. Add a third app next year, and it's 30. This is the part people miss: an LLM never actually calls an API. It just writes "please do X." Some piece of normal code — the execution layer — has to pick that up and actually make the call. Whether you use raw API docs or MCP, you're really just choosing how to build that execution layer. \*\*Option 1: Give the model API docs + a sandbox\*\* It works. The model writes code, chains the calls, handles Slack's channel-ID lookups and weird timestamp formats. But your team owns that code, the credentials, the sandbox, and every fix when Slack's API changes. \*\*Option 2: Connect to an MCP server\*\* The server already speaks Slack's API and exposes a clean menu: "read messages," "send message," "search by date." The model just picks an action — no low-level API knowledge needed. All that Slack-specific complexity now lives in one reusable place instead of being duplicated across every app. That's the actual unlock: 2 apps + 10 services = 12 pieces to build (2 clients + 10 servers), not 20 separate integrations. And every new app just plugs into the servers that already exist. Two honest caveats though: • Dumping every possible action into context still burns tokens — good MCP setups load only what's needed for the task. • API keys still live outside the model, in the execution layer. MCP doesn't make security automatic — your team still has to configure it right. So when do you actually need MCP? If it's one app calling a few APIs you already know well — a direct integration is fine, sometimes simpler. MCP starts paying off the moment multiple AI apps need to share the same systems. It's not new capability — it's a shared standard, so 10 apps can reuse one execution layer instead of building 10 of their own. The one-liner worth remembering: the model never executes anything. It just decides. Something else always does the work — the only question is whether you build that "something else" once, or ten times.
