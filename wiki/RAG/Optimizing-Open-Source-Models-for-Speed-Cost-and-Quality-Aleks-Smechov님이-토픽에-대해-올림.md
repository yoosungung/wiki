## Optimizing Open Source Models for Speed, Cost, and Quality

이 제목은 아래 게시물에서 AI가 요약한 것입니다.

At this point, it's not a question of whether you're using open source models in your stack, but which ones. Different models specialize in different things. Some are cheaper and faster to run and good for basic tasks like summarization and information extraction. Other open weights models challenge closed source incumbents in generalized intelligence. So how do you optimize for speed, cost, and output quality without hand-testing and cherry-picking models for thousands of different tasks in your org? Working alongside [Ihor Stepanov](https://ua.linkedin.com/in/ihor-knowledgator?trk=public_post-text) and his [Knowledgator](https://uk.linkedin.com/company/knowledgator?trk=public_post-text) group, [SCX ai](https://au.linkedin.com/company/southerncrossai?trk=public_post-text) jointly developed Router ([labs.scx.ai/router](https://www.linkedin.com/redir/redirect?url=http%3A%2F%2Flabs%2Escx%2Eai%2Frouter&urlhash=cdAW&trk=public_post-text)), an Apache 2.0 license, fine-tuned classifier based on a Qwen3-0.6B and GLiClass backbones. Running at under 50ms even on basic consumer GPUs, Router classifies each LLM input on 28 different task types (like summarization, forecasting, generation, planning...), potential difficulty and output length, and if the response needs reasoning (which can save lots of tokens). Then, using simple functions to balance speed, cost, and quality requirements, these attributes are used to select Primary and Backup models for inference. That could be any of [SCX.ai](https://www.linkedin.com/redir/redirect?url=http%3A%2F%2FSCX%2Eai&urlhash=9G5I&trk=public_post-text) 's 74 open weights models ([https://scx.ai/models](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Fscx%2Eai%2Fmodels&urlhash=Cis5&trk=public_post-text)), or closed LLMs like Opus 5. While this is unofficially our first announcement of our work, people are already finding and downloading Router on Hugging Face [https://lnkd.in/eJNMh94R](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Flnkd%2Ein%2FeJNMh94R&urlhash=g7Dh&trk=public_post-text), and someone has already created a Space for it [https://lnkd.in/eWY2Zede](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Flnkd%2Ein%2FeWY2Zede&urlhash=V9tN&trk=public_post-text). Really, this is our first prototype, and there's a lot (a lot) of work left in applying Router to coding (where it can make a large impact on costs) and improving overall classification accuracy on general-purpose tasks. But it's such an exciting start to a future where choosing a single model won't make sense, and where instead we'll get pools of hundreds of models competing to bring you the cheapest, fastest inference without compromising on output quality.

- 🚀 Launching Custom-DL-Optimizer v3.0.0 As part of my ongoing research in deep-learning compilers and hardware-aware AI inference, I have released Custom-DL-Optimizer, an open-source framework for selecting efficient PyTorch inference execution plans. The central idea is simple: do not assume an optimization is faster. Measure it. A transformation that accelerates one neural network can regress another. Compilation may improve steady-state latency while introducing substantial startup cost. Reduced precision may run faster but produce unacceptable numerical differences. Custom-DL-Optimizer treats available execution paths as competing plans, including: • PyTorch eager execution • AMP and channels-last layouts • PyTorch FX graph transformations • TorchInductor compilation • Torch-TensorRT • ONNX Runtime • TorchAO quantization • Custom or vendor-specific accelerator providers For representative workloads, the framework measures setup time, first-call overhead, latency distributions, memory usage, and numerical parity. It then uses deterministic bootstrap confidence bounds to replace the native baseline only when the measured improvement is sufficiently convincing. Version 3 also introduces weighted multi-shape workloads, lifecycle-cost analysis, persistent plan caching, heterogeneous callable runners, schema-versioned research reports, and bounded agent tooling. This project explores a broader research question: Can inference optimization become an evidence-driven decision process instead of a fixed sequence of compiler passes? The current release is a research beta. My ongoing work will focus on broader hardware evaluation, accelerator backends, controlled benchmarking, ablation studies, and comparisons with established inference systems. 📦 PyPI: [https://lnkd.in/duYA6dtp](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Flnkd%2Ein%2FduYA6dtp&urlhash=1_zj&trk=public_post-text) 💻 GitHub: [https://lnkd.in/d8X9zXJa](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Flnkd%2Ein%2Fd8X9zXJa&urlhash=Cmyj&trk=public_post-text) 🌐 Project site: [https://lnkd.in/d-3PYFjg](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Flnkd%2Ein%2Fd-3PYFjg&urlhash=XIqC&trk=public_post-text) pip install custom-dl-optimizer==3.0.0 Feedback, experiments, and contributions are welcome. - Which tokens should an LLM keep when it has to evict part of the KV-cache? I built a real KV-cache eviction benchmark on GPT-2-medium and compared: - full cache - sliding window - sink-preserving window - random eviction - attention-based eviction The results show two completely different regimes. At extreme compression (64-token cache budget): - sliding\_64 → perplexity 4138 - sink8 + window56 → perplexity 70 Same memory budget. Roughly 59× better quality just by preserving the first 8 sink tokens. But the bigger result came from the budget sweep. Best policy by cache budget: - 64 → sink8\_window56 - 128 → attention\_128 - 192 → attention\_192 - 256 → attention\_256 - 384 → attention\_384 At budget 256: - sliding\_256 → PPL 3300 - sink8\_window248 → PPL 43 - attention\_256 → PPL 1.88 - full baseline → PPL 1.02 At budget 384: - attention\_384 → PPL 1.02 - full → PPL 1.02 So attention-based eviction becomes essentially lossless while cutting KV-cache by about one third. The takeaway: - If your cache budget is tiny, preserve sink tokens. - If your cache budget is moderate, attention-based eviction is clearly better. - Plain sliding windows are the wrong policy. - Between 1996 and 1998 I burned an ungodly amount of time on Reed-Solomon error-correcting codes — the same math that lets a CD play through a scratch and a space probe phone home through noise. I worked from Phil Karn's implementation and tuned mine until I understood every table lookup. Somewhere in there I built a trick I called the "flipped" encoder: pick a symmetric generator polynomial and you can run the feedback loop in the cache-friendly direction. It was fast. It worked. And then life moved on. The code sat for 25 years. When AI got good, the first thing it did for me wasn't writing new code — it was reading my old code. It explained my own flipped encoder back to me, produced a readable reference implementation, and wrote down invariants I'd been carrying around in my head since the 90s. Then it started improving it. One generation of models cleaned up the architecture. The next vectorized the hot loop with NEON and AVX-512 — roughly 10× on syndrome calculation. And the latest releases did something I didn't expect: rebalanced the entire decode pipeline, caught a benchmark that had quietly been measuring the wrong thing for years, found real memory-safety bugs, cross-reviewed a C# port against the C++ original — each library fixing gaps in the other — and opened the repo's first pull request. Today: a full 255-byte codeword with 32 corrupted bytes decodes in under 10 microseconds on a laptop. Some of that is thirty years of hardware. But a real chunk landed in the last few weeks, on code I once believed I'd optimized to the bone. The part that gets me isn't that AI writes code. It's that it turned out to be the first colleague who ever read the whole thing — including the parts I'd forgotten I wrote.
