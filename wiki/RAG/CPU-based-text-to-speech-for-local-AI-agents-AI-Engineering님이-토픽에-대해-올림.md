## CPU-based text-to-speech for local AI agents

이 제목은 아래 게시물에서 AI가 요약한 것입니다.

Add text-to-speech to your AI agent without a GPU or an API call! Most TTS systems make you choose: pay for a cloud API or provision a GPU server. Neither is ideal when you're building a local agent pipeline or shipping something that needs to run on edge hardware. Pocket TTS from Kyutai runs entirely on CPU. At 100M parameters, it runs at 6x real-time speed using only 2 CPU cores, with around 200ms to first audio chunk. What it gives you: • Python API and CLI for generating audio from text in a single function call • Voice cloning from any WAV file or from a catalog of pre-made voices • Audio streaming so you can start playing before generation is complete • Multi-language support across English, French, German, Portuguese, Italian, and Spanish • Local HTTP server via pocket-tts serve with an OpenAI-compatible API for drop-in integration • In-browser support via WebAssembly community implementations • Handles infinitely long text inputs without chunking Works with any Python project. Someone compared LLMs to flex/bison — deterministic tools that transform input to output. Another commenter immediately pushed back: LLMs are non-deterministic by nature. Then a third person jumped in with actual [llama.cpp](http://llama.cpp/?trk=public_post-text) sessions showing that with a fixed RNG seed, you DO get reproducible output — even at temperature 20,000,000. Someone else pointed out that GPU thread scheduling and floating point precision mean "deterministic" depends entirely on your hardware and compiler flags. One commenter nailed it: "LLMs are a State -> Words transformer, that's all." They take a state and produce grammatically correct sequences. The temperature parameter isn't magic — it just biases the probability distribution before token selection. Low temperature exaggerates high-probability tokens. High temperature flattens things out. A PRNG picks the actual token. Another gem: the "preferred form of modification" question. If code is generated by an LLM, is the source code the preferred form, or is it the prompt? One person argued the prompt is like [configure.ac](https://www.linkedin.com/redir/redirect?url=http%3A%2F%2Fconfigure%2Eac&urlhash=_ZXB&trk=public_post-text) — you want the highest-level input. The actual Debian policy question is interesting too. They decided not to decide, which might be the smartest move. But honestly? - Ever watched a Kubernetes autoscaler try to scale an AI Agent loop using traditional REST rules? It’s pure chaos. 📉 In a standard REST API, traffic is a smooth stream where CPU spikes warn you to scale out. But with an AI Agent (like a React loop hitting Bedrock), the traffic profile is a heart attack: the agent sits quiet, suddenly fires 10 heavy tool calls into flight all at once, and then goes radio silent while waiting for I/O. Because the pod's CPU drops to near zero during that long wait, K8s thinks your pod is entirely idle and refuses to scale, leaving your event loop completely choked and saturated. The fix? Stop tracking CPU and start tracking instantaneous concurrency using Prometheus Gauges. By implementing a simple [gauge.inc](https://www.linkedin.com/redir/redirect?url=http%3A%2F%2Fgauge%2Einc&urlhash=9P5Q&trk=public_post-text) () right before your agent triggers its parallel tool burst—and a [gauge.dec](http://gauge.dec/?trk=public_post-text) () in a strict finally block when they finish—you expose the real bottleneck: in-flight queue depth. Feed this custom metric into your HPA via the Prometheus Adapter, set a hyper-fast 5-second scrape interval to catch the spikes, and you can finally auto-scale your agents before they hit a wall. 🤖🚀 [https://lnkd.in/ec2Pz6cp](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Flnkd%2Ein%2Fec2Pz6cp&urlhash=4xZU&trk=public_post-text)

- When I was building my custom "Inference engine" for my Hybrid Language model-based AI Assistant (CloneMe Core 26), almost everyone gave me the exact same advice: "Just use Ollama." It sounded great, but the moment I needed to hit strict latency targets on my 16GB RAM rig running on a Linux and Mac environment, the off-the-shelf frameworks completely collapsed. That is when it hit me: there is no perfect, universal framework out there, and there never will be. Optimising AI isn't just about dropping in a Python script. You have to actually align the hardware with the middleware. You are constantly fighting physical restrictions, like memory wall protection, and generic abstractions just add layers of latency that destroy real-time performance. Every single business requirement paired with a specific piece of hardware creates a completely unique puzzle.
